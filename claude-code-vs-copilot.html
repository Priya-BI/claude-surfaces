Copilot, Claude Code, and Fabric

Two agents, two meters, one boundary. Copilot in Fabric compared against Claude Code driving Fabric from a developer machine — over the Fabric command-line interface, or over a Model Context Protocol server — with the pros, the cons, and a routing rule for deciding which one a given task belongs to.

Written for the person who has to answer “so which do we use?” in a design review, and needs a defensible reason rather than a preference.

01“Copilot on Fabric” is three products, not one

The question “Claude Code or Copilot?” assumes there is one Copilot on Fabric. There are three, and they sit on opposite sides of the line that matters most. Getting this wrong is how a team ends up believing it has a governance property it does not have.

Plain language

The Model Context Protocol is a small standard that lets a program advertise a menu of tools — “list workspaces”, “run this query” — to an AI model, which then picks one and calls it. A program that does this is called an MCP server. Microsoft ships several for Fabric, and any agent can connect to them: Claude Code, GitHub Copilot in Visual Studio Code, or something you wrote yourself.

The three things people mean

  1. Copilot in Fabric. The chat pane and authoring help built into the Fabric portal — Power BI, Data Factory, notebooks, warehouse, Real-Time Intelligence. Runs on Azure OpenAI inside Microsoft’s environment. Billed to your Fabric capacity.
  2. Fabric data agents. An agent you build over a lakehouse, warehouse, semantic model or eventhouse. Usable inside Fabric — but Microsoft explicitly supports consuming one from outside, including as an MCP server, at which point it stops being an inside-the-boundary tool.
  3. GitHub Copilot in Visual Studio Code, pointed at Fabric. Install the Fabric extension and the Fabric MCP server and, in Microsoft’s words, “a Fabric agent mode becomes available in VS Code Chat.” This is a coding agent on a developer machine, reaching into Fabric over exactly the transport Claude Code would use.
The correction this page exists to record

Only the first of the three is what people are picturing when they say “Copilot keeps our data inside Fabric.” The third is architecturally the same shape as Claude Code — an outside agent on an outside machine — and differs from it on harness and vendor, not on data residency. The second can be either, depending on where you consume it from.

So the honest framing is not Claude Code versus Copilot. It is in-product agent versus outside agent, and Claude Code and GitHub Copilot are both on the outside.

The rest of this page compares box 1 with box 2 — Copilot in Fabric against Claude Code — because that is the comparison that actually trades one property for another. Where GitHub Copilot differs from Claude Code, it is noted inline.

02The boundary: where the rows end up

This is the axis that cannot be engineered away, so it goes first. Everything else on this page is a preference; this one is a property.

What Microsoft commits to for Copilot in Fabric

  • “Your data isn’t used to train models and isn’t available to other customers.”
  • “Data processed by Copilot in Fabric stays within your capacity’s geographic region, unless you explicitly allow data to be processed outside your region.” That permission is a tenant setting, and it is off by default.
  • Copilot “uses Azure OpenAI — not the publicly available OpenAI services”, and “the Service doesn’t interact with any services by OpenAI, such as ChatGPT or the OpenAI API.”
  • Abuse monitoring: “we no longer store prompt related data.” The 30-day retention that used to apply for abuse monitoring was removed.
  • “Copilot can only access data that the current user has permission to access.” Row-level security and workspace roles apply as they already do.
For the implementer

Two exceptions to “nothing is stored”. Copilot in notebooks and Fabric data agents do keep conversation history across sessions, because a conversational agent needs it. Microsoft: it “is stored inside the Azure security boundary, in the same region and in the same Azure OpenAI resources that process all your Fabric AI requests”, the user can clear it at any time, and “if the conversation history isn’t manually removed, it’s stored for 28 days.”

And a newer one: a tenant setting for “Copilot, AI Agents and other AI experiences powered by OpenAI as a Microsoft Subprocessor” now exists, disabled by default, with its own cross-region companion setting. Turning it on changes who processes your prompts. Microsoft points at a separate page for “data processing commitments, availability limitations, and compliance exclusions” — read that page before anyone flips it.

What is true for Claude Code, and for any outside agent

There is no equivalent commitment, because there is no equivalent architecture. The mechanism is worth stating concretely rather than abstractly:

The concrete version

You ask for last month’s failed orders. The agent runs a query — through the Fabric command-line tool, or through an MCP server, it makes no difference. A hundred rows come back: names, email addresses, order values. Those hundred rows are now in the request to the model vendor. An agent cannot reason about data it has not been given, so any answer about your data implies your data left Fabric.

This is the single most-conflated point in the whole comparison, so to be explicit: the command-line route and the MCP route are identical on this axis. Command output is read the same way tool results are. Choosing the CLI does not keep rows inside Fabric; it changes who picks the action and whether a rule can stand in between, which is a different and also real benefit.

On retention, the numbers usually quoted are the wrong ones. Thirty days is the API backend deletion window, not a cap on saved Team or Enterprise coding sessions, which are retained in-product until someone deletes them; and anything submitted as feedback — a thumbs-down, a bug report — carries a five-year window, on a commercial plan too. The companion page works through this in detail.

The axis nobody puts in the feature grid: who can see the prompt

Fabric records the API calls an outside agent makes. It does not record what the agent was asked, or what it said back — that conversation happens on the developer’s machine and at the model vendor, and your Fabric tenant never sees it.

For Copilot in Fabric, that conversation is inside Microsoft’s audit surface. Purview’s auditing for Copilot and AI applications generates records when a user interacts with Copilot, and Data Security Posture Management for AI is documented to capture user prompts, AI responses and interaction metadata across Fabric data agents and Copilot experiences.

Verdict on this axis: if the question is “can a regulator be shown what was asked of the AI and what it answered, on governed data?”, Copilot in Fabric answers it and an outside agent does not. That is not a tie you can close with configuration.

03The meter: which budget pays

People reach for “Copilot is included”. It is not. It is metered, and the meter it runs on is the same one your refreshes, queries and pipelines run on.

Copilot in Fabric bills in capacity units

OperationUnitConsumption rate
Input promptper 1,000 tokens100 CU seconds
Cached input promptper 1,000 tokens10 CU seconds
Output completionper 1,000 tokens400 CU seconds

Microsoft’s own worked example: a request with 2,000 input and 500 output tokens costs (2000 × 100 + 500 × 400) / 1000 = 400 CU seconds = 6.67 CU minutes. Copilot runs as a background job, so that cost is smoothed over 24 hours, and on an F64 “customers can run over 13,824 Copilot requests per day before they exhaust the capacity. Once the capacity is exhausted, all operations will shut down.”

Scale that down before you feel comfortable

13,824 requests a day is a lot — on an F64. Most teams reading this are not on an F64. The same arithmetic on an F2 gives 2 × 24 = 48 CU-hours a day and 48 / 0.111 ≈ 432 requests before the capacity is gone. That is my arithmetic, not Microsoft’s, using Microsoft’s method and Microsoft’s example request size.

And 432 is the number if the capacity does nothing else — no refreshes, no report queries, no pipelines. It is a ceiling, not a budget. Microsoft says the quiet part itself: “Deploying broadly without validating consumption patterns can quickly exhaust your capacity.”

Claude Code does not touch that meter. Its reasoning is billed against an Anthropic plan allowance shared with the other Claude surfaces; the only thing it puts on your capacity is the cost of the Fabric operations it actually performs, which you would have paid for if a human had typed them.

Verdict on this axis: Copilot’s cost is invisible until it is a throttling incident, and it lands on the budget of the platform team. Claude Code’s cost is visible, lands on a different budget, and cannot take a refresh down with it.

04Pros and cons, plainly

Same running order in both panels — what it is good at, then what it is bad at — so the lists compare row against row.

Copilot in Fabric

In-product · billed to capacity

Where it wins
  • Rows never leave. Processing stays in your capacity’s geographic region unless an admin explicitly allows otherwise, and nothing is used to train models.
  • The conversation is auditable. Prompts and responses land in Microsoft’s audit surface. No outside agent offers this.
  • Permissions come for free. It sees exactly what the signed-in user sees — row-level security, workspace roles and labels already apply.
  • Nothing to install, nothing to approve. No developer machine, no tokens on disk, no third-party server to review. An analyst can use it today.
  • It knows the item it is sitting in. Schema, measures, lineage and visuals are context it already has rather than context you have to feed it.
Where it loses
  • It cannot touch files. No repository, no diff, no commit, no test run, no continuous integration.
  • It works one item at a time. “Rename this measure across forty reports” is not a shape it has.
  • It spends your capacity. Output tokens cost four times input tokens, and an exhausted capacity shuts down all operations, not just Copilot.
  • It is on by default. The main tenant setting ships enabled, so on a paid capacity the decision to adopt Copilot may already have been made for you.
  • Quality caveats are Microsoft’s own. Responses “can include inaccurate or low-quality content”, and features “work best in the English language.”

Claude Code

Outside agent · billed to a plan allowance

Where it wins
  • Files are its native material. Point it at a git-integrated workspace and semantic models, reports, notebooks and pipelines become source it can refactor in bulk.
  • The work is reviewable. A diff, a commit, a pull request — the change survives the session and someone else can check it.
  • It composes with everything else on the machine. Tests, linters, the Fabric command-line tool, deployment pipelines, whatever your team already runs.
  • It does not compete with your refreshes. Reasoning bills to a different meter in a different budget.
  • It can be gated. Commands are visible text before they run, so a permission rule or a human can stand between the model and a destructive action.
Where it loses
  • Every row it reads leaves Fabric. True on the command-line route and the MCP route alike. This is the cost of the whole approach.
  • Fabric cannot see the conversation. Your tenant logs the operations, never the prompt or the answer.
  • It needs a developer. A machine, a login, tokens, and someone who reads a diff. An analyst is not going to adopt this on a Tuesday.
  • Identity is yours to get wrong. A shared service principal is the convenient option and the worst one: every action arrives in the audit log as the principal, not the person.
  • The MCP menu includes destructive tools. Deleting workspaces and granting workspace roles are on it, and Microsoft notes such safeguards “are not standardized in the MCP specification.”
The symmetry worth noticing

Each tool’s biggest weakness is the other’s headline strength, and neither weakness is a bug someone is going to fix. Copilot cannot edit files because it does not live where files are; Claude Code cannot keep rows inside Fabric because it does not live inside Fabric. That is why the answer to “which one” is usually “both, split by task” — and why the split has to be deliberate.

06When to use which

The tree below is ordered deliberately: hardest constraint to unwind first. A data-residency obligation is not negotiable, an audit requirement is negotiable only slowly, capacity headroom is negotiable with money, and convenience is negotiable immediately. Take the first branch that fires and stop.

Worked examples

TaskRouteWhy
“Explain what this measure is doing and why it double-counts”Copilot in FabricOne item, one person, no artefact to keep. Fewer keystrokes.
“Rename Sales Amt to Sales Amount everywhere and fix the reports”Claude CodeSpans items, needs a diff and a rollback path.
“Draft a first-pass report page over this model”Copilot in FabricIt already has the schema and can place the visuals in place.
“Add row-level security to nine models, consistently”Claude CodeConsistency is a file-level property, and someone must review it.
“Why did last night’s pipeline fail?”EitherCopilot if you are already in the portal; Claude Code if the answer becomes a fix.
“Summarise these customer complaint rows”Copilot in FabricThe rows are the sensitive part, and this is the branch where they must not leave.
“Stand up the same medallion layout in three workspaces”Claude CodeRepeatable, scripted, reviewable. Copilot has no shape for “do it three times identically.”

07Using both: the seam between them

If the answer is “both”, the interesting engineering is not in either tool. It is in the joint.

The joint is Fabric git integration

Claude Code is only useful on Fabric because Fabric will hand you your items as source — model definitions, report definitions, notebook code, pipeline definitions — in a repository. That is the surface it is good at. Copilot works on the deployed item in the portal. Both are legitimate, and they write to different copies of the same thing.

The operational trap

A portal edit and a repository edit are two uncommitted changes to one item, and whoever syncs second overwrites or conflicts. This is not an AI problem — it is the ordinary two-writer problem — but agents make it likely rather than rare, because both tools now produce edits faster than anyone reconciles them.

Decide per workspace which side is authoritative, and make the other side read-only in practice. A development workspace where the repository wins and Copilot is used for exploration only is a coherent rule. “Whichever is convenient” is not.

The other seam: a data agent as a governed door

A Fabric data agent can be published for consumption from outside — Microsoft names Foundry, Copilot Studio, Microsoft 365 Copilot, “or as an MCP server.” That is genuinely useful: retrieval stays inside Fabric, grounded on the items you chose, under the user’s own permissions, instead of an outside agent free-associating over your catalogue.

It does not repair the boundary, and Microsoft says so on the same page: when users connect to those non-Fabric services, “responses returned by Fabric data agents may be sent outside of Fabric’s compliance boundary or geographic region, and processed and/or stored according to the non-Fabric service(s) applicable terms and data handling policies.”

A data agent narrows what leaves and keeps the retrieval governed. It does not change that something leaves.

Hygiene that applies whichever way you go

  • Interactive, per-user login for interactive work. A shared service principal in an agent’s environment throws away per-user governance: every action arrives in the audit log as the principal, and Fabric can no longer tell your engineers apart. Reserve service principals for genuinely unattended automation, with their own least-privilege workspace role.
  • Do not point an outside agent at production data. This reduces exposure more than any other control on this page, and it outranks the rest of the list.
  • Ask for aggregates and narrow projections, not SELECT *. Less comes back, so less is transmitted and retained. Ask for the shape of the answer rather than the rows.
  • Audit the servers you install. The first-party Fabric MCP servers are Microsoft’s; a community server is third-party code you are handing a token to.
  • Review the Copilot tenant settings rather than inheriting them. The main one ships enabled; the subprocessor and cross-region ones ship disabled. Know which state yours are in and who changed them.
  • Watch the Copilot line in the capacity metrics app before rolling anything out broadly. Microsoft’s own advice is to pilot small and extrapolate.

08Where this could be wrong

The strongest objection to this page is to its own first branch, and it is worth making properly rather than gesturing at.

The counter-argument

I have made data residency the first question, which means it fires for almost anything touching real data — and on a data platform, almost everything touches real data. Applied literally, the tree routes nearly all work to the tool that cannot do most of the work, and a team that follows it ends up hand-editing forty reports because a rule said so.

The escape, and it has to be deliberate: the branch fires on rows, not on structure. Column names, model definitions, measure expressions and aggregates are not the regulated payload. An agent that reads a model definition and never runs a query has not moved a customer record. That distinction is what makes “both” workable — and if your team cannot hold it in practice, then the first branch really does swallow everything, and you should say so out loud rather than discover it later.

Four more places this could be wrong:

  • The prompt-audit claim is documented, not observed. Microsoft documents that auditing for Copilot and AI applications generates records, and that posture management for AI captures prompts and responses across Fabric Copilot experiences. I have not watched a real audit record for a Fabric Copilot session in a real tenant. Documented capability and what your tenant actually emits are different things — verify before you promise it to a risk committee.
  • The F2 number is my arithmetic. Microsoft publishes the F64 example. I scaled it linearly to F2. Smoothing and bursting behaviour at the small end may not be linear, and the example request size is Microsoft’s, not yours — a long conversation over a wide schema is much larger than 2,000 input tokens.
  • Rates move. Microsoft states plainly that consumption rates “are subject to change at any time”, with notice by email or in-product. Any capacity plan built on the numbers above needs re-checking, not re-quoting.
  • Much of both sides is in preview. Several Copilot workload experiences carry preview terms, the standalone cross-item Copilot is preview, and the remote Fabric Core MCP server is preview with “features and configuration may change.” A preview statement is a weaker commitment than a general-availability one.
Shelf life

Verified 2026-09-02. The volatile parts are the consumption rates, the tenant setting names and defaults — the subprocessor settings are recent additions — and preview status on both sides. The stable part is the shape: an in-product agent that cannot leave and an outside agent that cannot stay. Re-check the numbers; the shape will outlast them.
